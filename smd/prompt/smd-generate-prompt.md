**PROMPT START**

## 1. Role and objective

You are a senior front-end engineer and delivery analyst. Create **SMD (SDLC Monitoring & Dashboard)**: a **static, clickable, single-file HTML dashboard** that shows the full SDLC state of the **PMS (Payroll Management System)** project. PMS has four modules: EIMS, AMS, LMS and SMS. All data is derived from the project repository at **`D:\POC\PMS`**.

SMD is **read-only**. The repository is the single source of truth: it contains design artifacts, BMAD outputs, code, decision logs, agent memory and agent session logs. SMD reads the repo, condenses what it finds into one data block, and renders that data as a dashboard that:

- lives in the codebase at `D:\POC\PMS\smd\`, and
- can be **sent as an email attachment and opened on its own** (double-click, offline, any modern browser).

For any stakeholder, SMD must answer these questions within 10 seconds:

1. Where is the project now? (current stage, health, % complete)
2. What has been done, by whom, and when? (stages, steps, artifacts, authors, completion dates)
3. What is next, and what is blocking it? (upcoming items, gates, open gaps)
4. Do the artifacts agree with each other? (reviews, gaps between consecutive stages, coverage)
5. What changed since the last update?

## 2. Hard constraints

- **One self-contained HTML file.** All CSS and JS inline. **No CDN, no external fonts, no network calls.** It must work from `file://`.
- **Data is embedded** in a single `<script type="application/json" id="smd-data">…</script>` block. Browsers block `fetch()` of local JSON files, so never load data from a separate file at runtime.
- **The renderer is separate from the data.** Rendering code reads only from `#smd-data`, so a refresh replaces only the data block.
- **Vanilla JS (ES2020) and CSS only.** No frameworks and no build step for viewing. Charts are inline SVG generated by JS.
- Target file size **under 2 MB**. Embed artifact **summaries and metadata**, not full documents.
- Do not depend on localStorage. If it is used for UI preferences, wrap it in try/catch.
- Navigation uses hash routes (`#/stage/3`, `#/artifact/PMS-BRD-001`), so the browser back button and deep links work.
- Print-friendly CSS, so "Print / Save as PDF" of the Overview gives a one-page status report.
- Accessibility: WCAG AA contrast. Status is always shown with an icon and a label, never by colour alone. Keyboard-navigable.
- **Every artifact and code file is one click away.** See §2a.

## 2a. Links to the actual files

SMD is a dashboard *over* the repository. A user who has checked out the whole repo must be able to open **any artifact or code file** directly from the HTML page.

- Every artifact, review, decision, CR, story, agent memory / session log entry and code file in the data carries its repo-relative `path` (e.g. `docs/brd/PMS_BRD.md`, `services/lms/src/leave.controller.js`).
- The renderer builds each link **relative to the HTML file's own location**, `smd/web/` → `../../<path>`. The prefix is set once in the data (`meta.repo_rel_prefix: "../../"`), so the links keep working if the repo is cloned anywhere (any drive or folder) on Windows, macOS or Linux. **Never use absolute paths** like `D:\…` in links.
- Links open in a new tab (`target="_blank"`). Paths are URL-encoded per segment, so spaces and special characters work (e.g. `Claude outputs/…`).
- Each link shows a small file-type icon: `.md` / `.txt` / code files open as text in the browser, PDF and images render, and Office files (`.docx` / `.xlsx` / `.pptx`) download or open in the local app. Add a **"Copy path"** button next to each link.
- **Remote fallback:** if the repo has a git remote (e.g. GitHub), store `meta.remote_base_url` (e.g. `https://github.com/<org>/<repo>/blob/<branch>/`) and show a second "Open on remote" link. This helps when the HTML is opened as an email attachment outside a checkout.
- **Detached mode:** if the page is not inside a checkout (e.g. opened from Downloads), relative links will fail. Show a dismissible banner: *"Full artifact and code links work when this page is opened from `smd/web/` inside a checkout of the PMS repository."* Detect this best-effort: try loading `../../smd/web/.smd-anchor.png` (a 1×1 image written by `build.mjs`) via an `<img>` tag; if it fails, show the banner. Nothing else on the page may depend on this check.

```
 ├── CHANGELOG.md             # one entry per refresh: what changed
 └── README.md                # what SMD is, how to view, how to refresh
```

`build.mjs` must use only Node built-ins (`fs`, `path`). It:

1. validates `smd-data.json` against the expected shape (required keys present),
2. escapes `</script` inside the JSON,
3. creates `smd/web/` if it is missing and writes `smd/web/PMS_SMD_Dashboard.html` (plus `.smd-anchor.png`),
4. **checks every `path` in the data resolves to an existing file** relative to the repo root, and lists any broken links as warnings, and
5. prints the file size.

Nothing except generated viewable output goes into `smd/web/`. If more pages are ever added (e.g. a printable `status-report.html`), they also go in `web/` and must also be self-contained.

If Node is unavailable, the agent may do the injection directly. The output must be identical either way.

## 6. Data sources and precedence

For each field, use the first source available. Record which one was used in `source`:

1. **Declared:** YAML front-matter in the artifact, or a `reviews/`, `decisions/` or `crs/` file that follows CONVENTIONS.md → `source: "declared"`
2. **Config:** values set in `smd-config.yaml` (e.g. stage owners, planned dates) → `source: "config"`
3. **Git:** first commit = created, last commit = last updated, commit author = author → `source: "git"`
4. **Inferred:** read from content or file names (e.g. "Status: Draft" in a heading, or "_v1.2" in a name) → `source: "inferred"`. The UI shows these with a dotted "inferred" badge.

Rules:
- **Agent memory and session logs:** **summarize only** into `activity` entries (date, agent, one-line summary, file path). Never embed raw log text, prompts, secrets, credentials, personal data or salary figures.
- **Decision logs** → `decisions` entries (id, title, date, author, stage, one-to-three-line summary, path).
- **Code:** derive story / coding-step progress from story files (BMAD story status sections), branches and commits that reference story IDs, and test folders. Do not embed code contents. **Do index every tracked code and artifact file** in `repo_files` (path, folder, type, size, last commit date and author, linked story / artifact IDs taken from commit messages and front-matter), so the page can link to every file. Exclude binaries, `node_modules`, build outputs, `.git` and anything git-ignored. Exclude secrets files (`.env*`, keys) completely, not even their names.
- Use relative paths from the repo root (e.g. `docs/brd/PMS_BRD.md`).

## 6a. Token utilization (internal sections, PR-04, D-96)

- **Logging rule.** Token consumption is logged at **stage + outcome/artifact** level in `memory/usage/token-log.csv` (columns: `date, stage, outcome, module, activity, requests, input, cache_write, cache_read, output, total, source, ref, note`; `stage` is 0–8 or `X` for cross-stage governance and tooling; `source` is `measured`, `estimated` or `not-recorded`). The working session takes a cumulative usage reading at the start and at the completion of every outcome (typically its commit) and appends one row per outcome with the difference. Create the file with its header and a `memory/usage/README.md` if they do not exist.
- **Session readings.** Every cumulative reading is also kept in `memory/usage/session-readings.csv` (columns: `date, session, checkpoint, requests, input, cache_write, cache_read, output, total, instructions_pct, files_pct, documents_pct, conversation_pct, other_pct, source, ref, note`).
- **SMD reads, never writes** the logs, and never invents figures.
- **Rendering.** `build.mjs` aggregates the log (per stage: total, effective, requests; per outcome inside the stage: module, total, effective, requests, source, rows, last date) and injects it, with the session readings, into a second placeholder `/*SMD_TOKENS*/` of the template. There is **one dashboard**, `smd/web/PMS_SMD_Dashboard.html` (D-96). Its Overview shows a card "Token utilization – stage › outcome (internal view)" directly under "Timeline (actual)", with a share bar per stage, "not recorded" for unlogged outcomes, and a footer with total tokens, effective tokens (input×1 + cache write×2 + cache read×0.1 + output×5) and measured / not-recorded row counts.
- After it, a card "Token readings – whole session (internal view)" lists each session's cumulative readings (latest = session total so far) with tokens by type, effective tokens and the group split.
- **Sharing with the customer.** Both cards are internal; they are removed manually (all token code sits between `TK-START` / `TK-END` markers) before the dashboard is shared with the customer. Token figures never go into `smd-data.json`, snapshots or the changelog.

## 8. Screens (hash-routed, single file)

1. **Overview (`#/`)**
   - Header: app name, health badge with reason, current stage, go-live countdown, "Data as of" timestamp and commit.
   - **Pipeline strip:** stages 0–8 as clickable chevrons with status icon, dates and Manual/BMAD badge. The current stage is highlighted, and the "BMAD-ready" gate marker sits between stages 3 and 4.
   - KPI tiles: stages done / total, artifacts approved / total, stories done / total, open Critical/High findings, overdue items.
   - **Done / Doing / Next** columns, with author and date on every item.
   - **What changed since last update** (from `changes_since_last`).
   - Planned vs actual timeline (SVG Gantt-lite).
2. **Stage detail (`#/stage/{seq}`):** gate checklist with evidence links, steps (with BMAD agent role), milestones, artifact table (sortable and filterable by status, module, author), the findings that block the gate, and related decisions.
3. **Build matrix (`#/build`):** Story × 10 coding steps grid, grouped by epic and filterable by module, with roll-up percentages.
4. **Artifacts (`#/artifacts`, `#/artifact/{code}`):** a searchable register. The detail page shows metadata, summary, version, upstream/downstream chain (mini-flow), reviews, findings, and source badge, plus **"Open file"** (relative link), **"Open on remote"** (if available) and **"Copy path"**. Upstream and downstream items are also clickable file links.
4a. **Repository / Code browser (`#/repo`, `#/repo/{folder}`):** a collapsible folder tree of `repo_files`, with a filter by kind (code / test / config / artifact / log / memory) and module. Every file is a clickable link that opens the actual file. Each row shows its last-updated date, author and linked stories / artifacts. Story pages and Build matrix cells list the files touched for that story, as links.
5. **Reviews & Gaps (`#/gaps`):** a coverage matrix for consecutive pairs (Mockups↔BRD, BRD↔HLD, HLD↔Architecture, BRD↔PRD, PRD↔Stories, Stories↔Tests) and a findings list filterable by severity and status.
6. **Decisions (`#/decisions`):** decision log timeline.
7. **Activity (`#/activity`):** combined human and agent activity feed (commits, agent sessions, reviews, status changes), filterable by actor and type.
8. **Change Requests (`#/crs`):** CR intake list and CR pipelines with their own mini strips. Show an empty state before go-live.
9. **Trend (`#/trend`):** artifacts approved and stories done over time, from the snapshot history embedded in `meta` as a compact series.
10. **About / Data quality (`#/about`):** sources, counts of declared vs inferred values, warnings, and how to refresh.

UX: a persistent left nav, a breadcrumb, a global search box (artifacts, stories, decisions), a module filter chip row (All / EIMS / AMS / LMS / SMS) that applies across screens, and a light theme with a dark-mode toggle.
